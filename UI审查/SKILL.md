# UI 审查

定位：这是**诊断层**，不是造型师。它不改代码、不生成界面，只回答「哪里不对、违反了哪条规则、现在的实测值是多少、改成什么」。

一句话判别标准：**说不出规则号的就不算 finding，只是品味。**

## 0. 四条可移植性原则

1. **零网络依赖**：规则档随技能目录分发，断网可审。
2. **零包硬依赖**：`browser` / `code_runner` 等包探测到就用，探测不到自动降级（见 §3），降级后结论照样成立。
3. **零设备假设**：不假设屏幕宽度、不假设深色、不假设有构建链。先测再判。
4. **路径自定位**：`<SKILL_DIR>` = 本 SKILL.md 所在目录，Operit 默认 `/sdcard/Download/Operit/skills/UI审查/`。

## 1. Step 0：先检测，再判断

不做这一步，会犯两个最贵的错：跟项目已有的设计系统打架、给出项目根本用不上的写法。

| 要检测 | 怎么测 | 影响什么 |
|---|---|---|
| 技术栈 | 有无 `package.json`、`<script src>`、`<link rel=stylesheet>` | 决定用不用 Tailwind 类名描述改法 |
| 是否 Tailwind | `@import "tailwindcss"`（v4）vs `@tailwind base`（v3） | 决定改法的表达方式；**没有 Tailwind 就别提 Tailwind** |
| 已有 token | CSS 自定义属性、`tokens.json`、主题文件 | 有系统就用系统的词，别另立一套 |
| 暗色 | 是否有 `prefers-color-scheme` 或固定深色底 | 影响对比度基线 |
| 视口 | `meta viewport`、容器最大宽度 | 决定按 320 / 390 / 1280 哪种宽度取证 |
| 内容来自哪 | 静态 HTML，还是命令输出/接口数据 | 决定空状态、长文本、极值的检查项 |

**已有系统永远优先**。项目里已经有的颜色阶、间距阶、字号阶，就是本项目的「体系」；书里的默认阶只是备选，且用它要明说「项目没有体系，这里是回退到默认」。

## 2. 固定扫查顺序（不许打乱）

顺序有因果：层级没理顺，什么算「间距问题」就会跟着变；而间距一改，「这里要不要加边框」往往自己就没了。

| 步 | Lens | 读哪份 | 主要看什么 |
|---|---|---|---|
| 1 | 层级 | `references/02-hierarchy.md` | 谁是主操作、有没有靠「全都加粗」硬撑、灰字是否用在彩底上 |
| 2 | 间距 | `references/03-layout-spacing.md` | 组间距是否大于组内间距、值是否出自阶、移动端是否只是桌面塌缩 |
| 3 | 排版 | `references/04-typography.md` | 字号种类数、行长 45–75 字符、行高是否随字号变化 |
| 4 | 色彩 | `references/05-color.md` | 每个文本/背景对是否达 4.5:1（大字 3:1）、灰阶数量、饱和补偿 |
| 5 | 深度 | `references/06-depth.md` | 阴影是否来自固定集合、光源是否一致朝上 |
| 6 | 图像 | `references/07-images.md` | 图上文字可读性、小图标是否被放大、上传图是否有 `object-fit` |
| 7 | 收尾 | `references/08-finishing-touches.md` | 空状态、默认控件、强调边框、焦点态 |

- 前 3 步没结论就不要进第 4 步。
- 第 7 步（收尾）**必须等前 6 步的问题处理完**，否则会把「层级错」误诊成「缺个边框」。
- 暗色、焦点态、动效、`z-index` 属于书外扩展，见 `references/15-beyond-the-book.md`。
- 症状反查（「看着不对但说不上哪不对」）先查 `references/14-antipatterns.md`，它按「现象 → 规则」倒排。

## 3. 取证：先量，再说

**不许目测对比度、不许猜字号。** 同一份取数逻辑放在 `scripts/audit.js`，三种环境共享：

| 级别 | 条件 | 怎么做 | 能拿到什么 |
|---|---|---|---|
| L1 | `browser` 包可用 | `goto` 本地文件 → `resize` 390×844 与 1280×800 → `evaluate("() => " + <audit.js 全文>)` | 真实 computed style：实测对比度、字号/间距/圆角去重统计、tap target 尺寸、行长 |
| L2 | 无 browser，有 JS 执行手段 | 读 `index.html` 的 `<style>` 与外部 CSS，喂给同一份 `audit.js` 的计算函数 | 静态值（不含继承与媒体查询的实际生效值） |
| L3 | 都没有 | 把 `audit.js` 交给用户粘进任意浏览器控制台，回收输出 | 同 L1 |

硬规定：**每条 finding 都标注取数方式（渲染 / 静态 / 控制台）**。静态推断不能写成实测。

报告里还有两个字段决定"能不能下结论"，必须读懂再用：

- `incomplete[]`：无法判定的项（`bgGradient` / `bgImage` / `imgNode` / `colorParse`）。这些项**不许**自己补一个背景色去算对比度——直接进 finding 表的「存疑」列，并说明原因。对照 axe-core 的 `incompleteData`：给出一个错误的确定值，比承认判断不了更糟。
- `measure[]`：行长数据。三个字段决定它能不能当作证据：
  - `approx: true` —— 行高取自 `line-height: normal` 的 1.2em 估算，引用时须注明是估算。
  - `lowConfidence: true` —— 行数 < 3，末行填不满会让「字符数 / 行数」系统性偏低（实测 25 字折 2 行算出 12），**不能**据此判「行长过短」。
  - `note: narrow-viewport(...)` —— 视口 < 768px。45–75 字符是桌面正文档位的标准；窄视口下每行 20–30 字符是设计结果，套这个阈值等于每个段落都超标。

自检口径：`contrast.checked === passed + failed` 才算完整；`incomplete` 非空、`incompleteTruncated` 或 `truncated` 为 `true` 时，结论不能是"全部合格"。

### 已知局限（宁可不报，不要误报）

- **被其他元素遮挡的文字**：未做 `elementFromPoint` 校验（axe 会标 `elmPartiallyObscured`）。浮层压住的文字可能得到偏乐观的对比度。
- **文字描边 / text-shadow 提升可读性**：未计入（axe 有 `get-text-shadow-colors`）。纯靠描边可读的文字会被算成低对比。
- **渐变 / 图片背景**：一律进 `incomplete`，不猜——这是设计选择，不是缺陷。
- **`charsPerLine` 对中英混排只是粗估**：等宽与比例字体、中英文宽度差异都会带来误差，只作量级参考。
- **`::before` / `::after` 生成的文字**不在 DOM 遍历范围内，不会被检查。

遇到上面这些情况，正确做法是写进 finding 的「存疑」列，而不是绕过去给个数字。

Android WebView / KernelSU 类 WebUI 的额外一步：页面依赖宿主注入的 `ksu` 全局对象，直接打开会抛错、后续 DOM 不更新，取数会失真。取数前先注入 stub：

```js
// 注入后再取数：只为让页面脚本跑完，不代表这些命令会真的执行
window.ksu = window.ksu || { exec: async () => ({ errno: 0, stdout: '', stderr: '' }),
                             toast: () => {} };
```

## 4. finding 格式（缺字段就不是 finding）

```
| # | Lens | 严重度 | 位置 | 规则 | 现状（实测值） | 建议 | 工作量 | 取数方式 |
```

- **规则**：必须写 `§n.n`，且该编号能在 `references/` 里查到。写不出编号 → 丢弃，或降级为「观察」单列。
- **现状**：带数值。不是「间距偏小」，而是 `组间 8px / 组内 8px`。
- **工作量**：S 一行 / M 一个组件 / L 系统性。
- **取数方式**：渲染 / 静态 / 控制台。
- 排序：按严重度降序；同级别按扫查步骤顺序。

上游 rubric（`references/13-audit-rubric.md`）有完整字段定义与逐 lens 检查表，**开始扫查前先读它**。

## 5. 严重度

- **P0 · 影响可用性**：层级崩塌看不出这页干什么；对比度不达 4.5:1 / 大字 3:1；只靠颜色传意；图上文字部分不可读；组间距歧义到会输错数据；正文行长远超 45–75 字符；破坏性操作被做成页面主操作；支持宽度下布局崩了。
- **P1 · 影响一致性**：脱离体系的值（任意 px、一次性颜色）；超过 3 种文字色或 2 种字重；彩底灰字；一页多个「主操作」外观；圆角不统一；阴影逐组件手写；行高全场统一；大写无字距；图标与相邻文字同色；同行混字号但居中对齐。
- **P2 · 打磨**：空状态缺失（功能类算 P0）、默认控件、强调边框、焦点态、细微不对称。

**P0 一律越界上报**，即使你被问的是别的问题。

允许输出「查过，合格」，并附实测值作为合格依据——不硬凑条数。

## 6. 十二条铁律（常驻，不必查档）

1. 层级就是设计本身，不是配色问题。`§2.1`
2. 主元素不够突出时，削弱竞争者，别加强主角。`§2.4`
3. 每个数值都出自体系：字号、间距、颜色、阴影、圆角、边框宽。`§1.5 §3.2 §4.1`
4. 留白先给多再往回收，反过来一定不够。`§3.1`
5. **组间距必须大于组内间距**——这一条修掉大部分「说不清哪别扭」。`§3.6`
6. 尺寸不是唯一杠杆：两档字重（400/500、600/700）+ 三级文字色，能承担几乎全部层级。UI 文字不低于 400。`§2.2`
7. **彩色背景上不要用灰字**，要的是降低对比，不是变灰。`§2.3`
8. 一页一个主操作；破坏性操作不因为它破坏就自动变大。`§2.8`
9. 按语义选元素（h1 是结构），按层级给样式。`§2.6`
10. 光来自上方：凸起=上边缘亮+下方小锐影；凹陷=上方影+下边缘亮。`§6.1`
11. 正文 45–75 字符（20–35em）；行长越大行高越大，字号越大行高越小。`§4.3 §4.5`
12. 不要只靠颜色传递信息。`§5.7`

## 7. 移动端 / WebView 专项（本类界面最常见的失守点）

- 无 `meta viewport` → 整页按桌面宽度渲染，手机上一律不可用。P0。
- 支持宽度下测 320px：按钮是否还够宽、文字是否溢出、横向是否出现滚动。
- tap target 实测高度 < 44px，或相邻按钮间距过小 → P1（点到错的按钮比不点更糟）。
- 深色主题要重算对比度，不能沿用浅色的灰阶（`#9aa0c0` on `#0f1220` 这类必须实测）。
- 固定像素的 `height` 配 `overflow: hidden` 会切掉长文本；命令输出用 `white-space: pre-wrap` + 容器滚动。

## 8. 明确不做

- **不改代码、不生成界面**：产物是 findings 表 + 系统性问题 + 优先级。
- **不装 Tailwind、不迁移样式方案、不替换已有设计系统**。
- **不评价内容与文案**（除非文案本身就是层级问题）。
- **不用「AI 味」当理由**：说得出规则才写，说不出就不写。
