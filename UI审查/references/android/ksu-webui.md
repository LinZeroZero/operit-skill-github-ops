# KernelSU 类 WebUI 的视觉审查清单

这类页面是「模块配置面板」：**一个页面、三到六个操作、一块输出区**。审查它们与审普通网页的差别在于——它永远在手机竖屏、永远在深色管理器的 WebView 里、用户永远是一只手操作。

本档只列视觉与可用性。代码与安全（`ksu.exec` 返回值、注入、XSS）走 `代码审查` 技能的 `android/ksu-webui.md`。

## 0. 取数前必须先做的两件事

1. **注入 `ksu` stub**，否则页面脚本抛错、DOM 不完整，取到的数值不可信（细节见 SKILL.md §3）。
2. **确认视口**：管理器 WebView 通常没有地址栏，但状态栏与手势区会占用高度。审查按 390×844 与 320×640 两个宽度各看一次——320 是「按钮还点得到吗」的下限。

## 1. 层级（§2）

- 一屏里是否有**一个**明确的主动作？三个按钮全用实心同款样式，等于没有主次 → P1（§2.8）。
- 「恢复默认」「清空」这类破坏性操作，与「查看状态」是否有区别？破坏性操作**不该**靠更醒目来表达，通常应是描边或文字按钮 → P1（§2.8.1）。
- 标题与操作区之间若只有一个字号差、没有间距差，层级是靠字号硬撑的 → 对照 `02-hierarchy.md`。
- 输出区（`<pre>`）在层级上属于「结果」，不该比操作区更抢眼。若它有纯黑底 + 高对比字，往往盖过按钮 → P2。

## 2. 间距（§3.6）

- **组间距 > 组内间距**是唯一必查项：三个同类按钮之间 8px，而按钮组与输出区之间也是 8px，就属于「分组失效」。手机面板里这条最常错。
- 面板整体 padding 是否明显小于元素间距？若 `padding: 16px` 但元素间距也是 16px，边界与内部分组混同（§3.1）。
- 所有间距是否来自同一档（4/8/12/16/24）？出现 13px、14px 这种一次性值 → P1（§3.2）。

## 3. 排版（§4）

- 面板正文 13px 在 390px 宽下勉强可读，320px 下偏紧；**命令输出区 12–13px 属合理**（它是等宽文本），但正文与按钮文字低于 14px 就该问一句为什么。
- 字号档数：模板自带的 `h3` 默认字号（约 18.72px）不是「选择」，是「没选」。若标题字号来自标签默认值 → P1（§2.6）。
- 行高全部是 `normal` → 长文本（命令输出、说明文字）显挤，P1（§4.5）。输出区应显式给 `line-height: 1.4–1.6`。
- 中文 + emoji 混排时，emoji 会撑大行高并在部分字体下错位；图标位置一致性属 §2.7.1。

## 4. 色彩（§5）

- **深色面板必须重算对比度**，不能套用浅色的灰。实测基准（`scripts/audit.js`，WCAG 公式）：`#9aa0c0` on `#0f1220` = **7.24:1**；同一灰字搬到按钮底 `#1c2138` 上 = **6.17:1**（仍合格）；白字 on `#1c2138` = 15.86:1。也就是说深色面板里，灰字的风险不在「深」，而在**灰阶本身选得偏暗**。
- 强调色当文字用时要看字号：`#7c4dff` on `#0f1220` 实测 **3.87:1**——作为 700 字重、18.72px 的标题刚好过 3:1 大字线；**一旦字号降到 18px 以下或字重降到 400，就不合格**。这是「同一颜色在两种用法下一个合格一个不合格」的典型。
- 文字色种类上限 3 种（§2.2）。标题一色 + 正文一色 + 次要说明一色，正好用满；再加一种「强调色」就超了。
- 强调色（紫/蓝/青）大面积使用前先问：这是**主操作**还是**装饰**？装饰性色块会抢走主操作的注意力（§2.8）。
- 状态信息（成功/失败）不能只靠颜色区分，要有符号或文字（§5.7）。

## 5. 深度与外观（§6）

- 深色界面里阴影几乎不可见，深度应由**表面明度差**表达（§6.4.1）。给按钮加 `box-shadow` 在纯黑底上等于没加。
- 圆角是否统一？按钮 10px、输出块 8px、卡片没有圆角 → P1（§1.4.3）。
- 边框与背景同时承担分隔时，留一个就够（§8.5）。

## 6. 收尾（§8）

- **空状态/初始状态**：输出区默认写「等待操作...」就是合格的初始态；留空白则是 P2（若它承担主要信息则 P0）。
- 失败态有没有独立呈现？只把错误文字塞进同一个 `<pre>`，用户会以为是正常输出（§5.7 的延伸）。
- 长任务时按钮是否进入禁用/加载态？没有的话用户会连点（可用性，非纯视觉）。
- 系统默认控件（`<button>` 未重置样式）会带浏览器默认外观，在深色下常出现浅灰底 → P2（§8.1）。

## 7. 典型 finding（可直接对照）

| 症状 | 规则 | 严重度 |
|---|---|---|
| 三个按钮全实心同款，无法看出主次 | §2.8 | P1 |
| 按钮组间距 = 组与输出区间距 | §3.6 | P1 |
| 标题字号是 h3 默认值，非选定档 | §2.6 | P1 |
| 行高 `normal`，输出区挤成一团 | §4.5 | P1 |
| 文字色 4 种 | §2.2 | P1 |
| 圆角 10px 与 8px 混用 | §1.4.3 | P1 |
| 深色底上的阴影看不出层级 | §6.4.1 | P2 |
| 输出区默认留空 | §8.4 | P2 |

实证样本（一次真实取数，390×844，含人工注入的三类测试块）：字号 3 档（16 / 13 / 18.72px，其中 18.72 是 `h3` 默认值）、字重 2 档（400/700）、文字色 4 种、padding 两档（14 / 12px）、圆角两档（10 / 8px）；10 组文本中 8 组达标、2 组失败（注入的低对比块 1.1:1、默认蓝链接 1.98:1）；1 组因渐变背景进入 `incomplete: bgGradient` 而**拒绝判定**；无 tap target 低于 44px。

注意 `sizes[].count` 是**元素数**不是"使用次数"（16px 会出现十几次，因为继承同值的元素都算），判断"几档"要看去重后的档数，别看 count。

**这类数据就是「实测」与「目测」的分界。**

## 8. 边界

本档不判断「这个模块该不该存在」「按钮该不该合并」。它只回答：在手机竖屏与深色环境下，这个面板能不能被看懂、能不能被点对。
