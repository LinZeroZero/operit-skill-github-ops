# shell 与 Android root 模块脚本

审 `*.sh`、`module.prop`、模块目录结构时读这份。**优先级高于任何上游语言档**：
上游的 shell 最佳实践默认你在 Linux 上跑，而这里跑在 Android 的 `mksh` + toybox/busybox 混编环境里，且常常没有 `$HOME`、没有写权限、没有常驻父进程。

本档只写**判定方法**。凡「本机有没有某个命令」这类事实，一律现场探测，不引用任何机型结论。

## 1. 先看模型：这东西有没有「还原」

有 apply 就必须有 restore，且两者对称。抓三类错：

- **备份只写一次**：`[ -f "$BAK/f" ] || cp "$f" "$BAK/f"` —— 缺了这个守卫，第二次 apply 会把「已改后的值」当成原始值备份，restore 再也回不去。这是本类脚本最常见、也最难事后察觉的破坏。
- **备份键会撞**：用路径扁平化做备份名（`tr '/' '_'`）时，`/##a` 与 `/#_#a` 会撞成同一个键。判定：把两三个真实路径代入扁平化规则手算一次，看是否唯一。
- **restore 漏项**：apply 改了 N 处，restore 只恢复 N-1 处。判定：把 apply 里所有写入点列成表（文件 + 值），逐个到 restore 里找对应的恢复语句，缺一个就是 🟡（若该项影响硬件状态则 🔴）。

## 2. 时机：文件放在哪个位置，决定了它什么时候跑

| 文件 | 时机 | 能依赖什么 | 典型误用 |
|---|---|---|---|
| `post-fs-data.sh` | 最早，`/data` 已挂载、Zygote 未起 | 只能做文件操作，**不能**等待服务 | 在这里 `sleep` 等系统服务起来 → 拖慢整个开机 |
| `service.sh` | late_start，系统基本就绪 | 可以起后台进程、等 sysfs 出现 | 在这里改 `/system`（已只读） |
| `boot-completed.sh` | 开机完成广播后 | 可依赖大多数服务 | 依赖它做「必须早于某 App」的事 |
| `action.sh` | 用户点模块按钮 | 交互式、短时 | 放长任务，用户切走就被挂起 |
| `uninstall.sh` | 卸载时 | 只能做清理 | 忘了还原被改的系统值 |

判定句：**这段代码要求的目标状态，在它运行的时刻是否已经存在？** 存的（如 `/sys` 下的节点）就 `[ -e ]` 判定；不存在的就等待并设超时，别假设。

## 3. 外部命令：全部当成「可能不存在」

Android 上没有 GNU coreutils。同一个 applet 在不同 ROM 的 toybox / busybox 里选项集不同：`flock` / `setsid` / `timeout` / `nproc` / `taskset` 到底有没有、`stat -c` 的格式符、`ps` 的参数风格，都只能现场看。

（本机 Android 16 + toybox 实测这几个都在——但那是这一台的事实，写进审查结论时仍要标明"在哪台设备上验过"。本档不给跨设备的通则。）

判定顺序：

```sh
command -v flock >/dev/null 2>&1 || echo "no flock：单例要换方案"
ls -l /system/bin/toybox /system/bin/busybox 2>/dev/null   # 谁在场
toybox 2>/dev/null | head -5                                # 可选 applet 概览
```

三条硬判据：

- **用了但没探测的 applet** → 🟡。如果它只影响体验（彩色输出），降 🟢；如果它在失败路径上（如 `flock` 缺失导致双实例），升 🔴。
- **`sed -i` / `grep -P` / `readlink -f` 这类 GNU 习惯** → 逐个实测，不实测就进「存疑」。
- **shebang 与实际运行时不一致**：写了 `#!/bin/bash` 但 Android 没有 bash，只有 `mksh`（`/system/bin/sh`）。这是 🔴，因为整份脚本可能根本没跑起来，而某些启动方式会静默忽略。

## 4. 后台进程：起了不等于活着

`cmd &`、`nohup cmd &`、`( cmd & )` 三种写法在 Android 的启动链里存活能力不同，取决于父进程退出时是否清理进程组。判定方法不是背书，而是**验证**：

```sh
# 起一个自增日志的守护，等 30 秒后看它是否还在推进。
# setsid 未必存在（先 command -v）；没有就退回裸后台——那就更该验证存活，而不是假定。
if command -v setsid >/dev/null 2>&1; then
  setsid sh "$MODDIR/daemon.sh" >/dev/null 2>&1 &
else
  sh "$MODDIR/daemon.sh" >/dev/null 2>&1 &
fi
sleep 30; tail -2 "$LOG"; pgrep -f daemon.sh
```

审查要点：

- 有没有**单例**？`flock -n 9` 最省；退而求其次 pid 文件 + `kill -0` 校验。缺单例的常驻脚本在多触发路径下会叠加（模块按钮 + 开机 + WebUI 各触发一次）。
- 有没有**退出条件**？`while true` 无 sleep 是 🔴（烧电）；有 sleep 但没上限、没网络/状态检查的，至少 🟡。
- 日志会不会无限增长？必须轮转（`mv log log.1` 或按大小截断），否则 🟡，长期跑变 🔴。
- 循环内的 `$(...)`、`|`、`cat` 都是 fork。稳态每轮 fork 数应能数出来；数不清就是设计问题。

## 5. 写入与失败：静默丢错是最贵的 bug

- 写 sysfs 用 `>` 还是 `echo`？两者都可能失败而无返回值被检查。判定：写入后**回读比对**，或至少保留 stderr。
- `2>/dev/null` 用在哪？用于「预期会失败且无害」的探测可以；用于写入操作就是 🟡（把真实失败也吞了）。
- `set -e` 在 Android 启动脚本里有风险（脚本被 source 时会影响调用方）。判定：出现 `set -e` 且脚本被 source → 🟡；独立执行且对失败敏感 → 可接受，但要确认每个命令的失败语义。
- 写入值要 `validate`：把手机不支持的值写进 `scaling_max_freq` 之类节点，内核可能接受并造成频率锁定；读者要能看出「这个值从哪来、为什么是这个值」。

## 6. 权限、路径与卸载

- 脚本里出现绝对路径 `/data/adb/modules/<自身 id>/...` → 换 `$MODDIR`（`${0%/*}`）或模块自身变量，否则改模块 id 时静默失效。
- 出现 `rm -rf "$VAR"`：`$VAR` 为空时等于 `rm -rf /`。判定：变量在赋值前是否有 `set -u` 或 `[ -n ]` 保护。无保护 → 🔴。
- `/sdcard`（FUSE）可能 **noexec**：放在那里的脚本只能用 `sh 脚本` 调用，`./脚本` 会 permission denied。若脚本内部再 exec 自己目录里的东西，要单独验证。
- 卸载/升级路径：模块被卸载后，改过的系统值还在吗？升级覆盖模块文件时，`backup/` 会不会被一起清掉？这两个问题各对应一条 finding。

## 7. 自查清单（逐条回答「是/否/不适用」）

1. apply 与 restore 是否逐项对称？
2. 备份是否只写一次？
3. 每处写入是否可回读验证？
4. 用到的每个外部命令是否探测过？
5. shebang 与目标运行时是否一致？
6. 常驻进程是否有单例、退出条件、日志轮转？
7. 稳态每轮 fork 数能否数清？
8. 所有删除路径是否有空值保护？
9. 路径是否都用 `$MODDIR` 派生？
10. 卸载/升级后系统状态是否可预期？

## 8. 边界

本档不评价「该不该改这个系统值」——那是功能决策。本档只判：这段脚本在目标运行时**会不会按它写的样子执行**，以及失败时可不可恢复。
